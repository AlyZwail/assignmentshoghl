# Two-player messaging

A single Maven project implementing the two requested execution modes in plain Java.
Production code has no external dependencies. JUnit is used only for tests.

## Requirements and commands

Use JDK 17 or newer and Maven 3.9 or newer. The first build requires access to
Maven Central to download build plugins and test dependencies.

```sh
mvn test
./start.sh same-process
./start.sh separate-process
```

Run commands from the project directory. The shell script also works when invoked
from another directory. It compiles the code and launches Java without building a
JAR. Its default mode is `same-process`. On systems that do not preserve executable
permissions when extracting ZIP files, use `sh start.sh same-process`.

Both modes print ten replies and two summaries showing each player's PID and
`sent=10 received=10`. In same-process mode the PIDs match; in separate-process
mode they differ. A failed run exits with a nonzero status.

## Behavior and decisions

The initiator begins with `Hello`. Each player appends ` | N` whenever it sends,
where N is its own one-based sent-message count, including the initial send.
For example:

```text
initiator sends: Hello | 1
responder sends: Hello | 1 | 1
initiator sends: Hello | 1 | 1 | 2
responder sends: Hello | 1 | 1 | 2 | 2
```

The initiator stops immediately after receiving its tenth reply. It does not
reply to that final message, so it never sends an eleventh message. Both players
finish with ten sends and ten receives. There is no extra application-level stop
message that could affect these counts.

The two execution modes are treated as two required alternatives, selected by a
command-line argument. The same-process requirement does not require separate
threads: sequential calls are sufficient for this strictly alternating exchange.

## Responsibilities and design

- `Player` owns a player's name and independent message counters, and appends its
  send counter to a payload. It has no dependency on sockets or process creation.
- `Exchange` represents one request/reply operation.
- `Conversation` runs the initiator's ten round trips through an `Exchange`.
- `SocketExchange` handles UTF-8 line framing, flushing, EOF, and socket ownership.
- `Main` selects the mode and manages player, socket, and child-process lifecycles.
- `PlayersTest` verifies counters, message progression, failure propagation,
  complete runs, PID relationships, and termination.

In same-process mode, an `Exchange` lambda passes the message to a second Player
instance and returns its reply. No queue or thread is needed.

In separate-process mode, the parent JVM contains the initiator and starts one
child JVM containing the responder. The parent binds a server socket to an
OS-assigned loopback port **before** launching the child, avoiding port collisions
and startup sleeps. Both modes use the same `Player` and `Conversation` logic.

The messages generated by this program contain no newlines, so UTF-8 lines are
sufficient framing. The writer rejects newline-containing payloads. This is a
local demonstration, not a general-purpose or authenticated network protocol.

After ten replies the parent closes the connection. The responder observes EOF,
checks its totals, closes resources and exits. The parent waits for successful
child termination. Connection, accept, read and process-wait timeouts are ten
seconds to prevent indefinite waits on failures; timeout duration is a developer
choice. Resources use try-with-resources. On failure the parent terminates a
remaining child, forcibly only if normal termination does not complete.

## Validation and delivery

`mvn test` runs unit tests and launches the real application in both modes.
The integration tests check exit status, ten replies, both players' totals, and
one versus two distinct PIDs.

Submit the source ZIP as an email attachment. Include `pom.xml`, `README.md`,
`start.sh`, and `src/`. Exclude `.git/`, `target/`, downloaded dependencies,
compiled classes, and JARs. No external download link is needed by the recipient.
